# L'assistente: `engine-ai`

`engine-ai` e' tutto cio' che un assistente con strumenti ha bisogno di fare **senza sapere cosa
fa l'app**: parlare con i provider, custodire le chiavi, reggere un flusso che si spezza, scegliere
il modello giusto per il compito, far girare i tool e tornare con una risposta e la sua traccia.
Nasce dal `core-ai` di FluidWeather, che Fluid Transit aveva copiato pari pari: la terza app ha
smesso di copiare e ha spostato qui la parte comune.

Package `dev.antigravity.fluidengine.ai`. Nessuna dipendenza da Compose. Dichiara `RECORD_AUDIO`
nel proprio manifest, perche' la voce e' parte del pacchetto: un'app che lo include ha il permesso
nel manifest fuso e lo chiede a runtime solo quando serve.

## Cosa c'e' dentro

| package | cosa |
|---|---|
| `net` | `AiHttp` (POST JSON, POST in streaming SSE, multipart, GET) su `HttpURLConnection`, `SseParser`, `MultipartBody`, `AiError` e la mappa degli errori/limiti, gli helper `JsonElement` |
| `provider` | il modello neutro (`Message`, `ContentPart`, `ChatRequest`, `ChatDelta`, `ToolSpec`), `ChatProvider` e i tre adapter (`GroqProvider`, `GeminiProvider`, `OpenRouterProvider`), i cataloghi, `ModelTier` con `TierDefaults` e `ProviderCapabilities`, `ProviderFactory` |
| `keys` | `AiKeyStore` (chiavi cifrate col Keystore in un DataStore proprio), `AiSettingsStore` (interruttore, ordine dei provider, modelli per livello, consenso), `AiKeyVerifier` (una `GET /models` vera), `ModelCatalogStore` |
| `tools` | `AiToolGroup`, `AiTool<C>`, `ToolOutput`, `ToolRegistry<C>`, `Schema`, `Args`, `ToolText` |
| `orchestrator` | `AiRouter` (stadio 1), `AiOrchestrator<C>`, `FailoverPolicy`, `TimeBudget`, `HistoryCompactor`, `Conversation`, `AssistantState`, `AiConfirmationGate`, `AiDiagnosticsLog`, `ChipParser` |
| `speech` | `SpeechCapture` (PCM con rilevamento del parlato), `AndroidPcmSource`, `Transcriber` (Whisper via provider, con failover) |

## Il contratto con l'app

L'app scrive **solo il suo dominio**:

1. **I gruppi**, un enum che implementa `AiToolGroup` (`id` per il modello, `statusKey` per la UI,
   `hint` per il router). Uno di essi puo' essere il gruppo delle azioni, che sparisce quando
   l'utente le ha spente.
2. **Il contesto** `C`: la classe con cui i tool toccano i dati dell'app (repository, ora, azioni).
3. **I tool**, `AiTool<C>`: nome, gruppo, descrizione, schema dei parametri (`Schema.obj(...)`), e
   `run(args, ctx): ToolOutput`. Il testo torna al modello com'e'; le `parts` (immagini, un PDF)
   le gestisce l'orchestratore.
4. **Il prompt di sistema**, con le regole e il contesto vivo, e i chip `[[id]]` che riconosce.
5. **Le azioni e le conferme**: i tool che scrivono passano da `AiConfirmationGate.ask(...)`, la UI
   osserva `gate.current` e chiama `resolve`. L'oggetto dell'azione resta nell'app.
6. **La UI**: overlay, impostazioni, consenso. L'engine espone lo stato (`AssistantState`), non lo
   disegna.

```kotlin
val registry = ToolRegistry(tools = allTools, groups = RegistroGroup.entries, actionGroup = RegistroGroup.APP)
val router = AiRouter(RegistroGroup.entries, RegistroGroup.APP, "il registro elettronico di uno studente", defaultGroups = listOf(RegistroGroup.VOTI))
val orchestrator = AiOrchestrator(registry, router, diagnostics, config = AiOrchestratorConfig(totalBudgetMillis = 240_000))

val result = orchestrator.ask(
  AskInput(
    question = question, mode = AskMode.TEXT, language = "it", settings = settings,
    providers = factory.ordered(ProviderFactory.Kind.CHAT), toolContext = ctx,
    systemPrompt = PromptBuilder.build(ctx), conversation = conversation, actionsEnabled = settings.actionsEnabled,
    preselectedGroups = preRouter.decide(question),      // null = lascia fare allo stadio 1
    chipFilter = { it.id in knownChips },
    attachmentFallback = { part -> pdfText.extract(part) }, // quando il modello non legge i documenti
  ),
  state,
)
```

## Il giro

```
domanda ─► pre-router dell'app (opzionale) ─┬─ gruppi decisi ───────────────────────┐
                                             └─ AiRouter (modello ROUTER, JSON) ─────┤
                                                                                     ▼
          CHAT: loop dei tool (gruppi scelti + altri_tool + modello_avanzato), N giri, 4 tool in parallelo
                                                                                     │
      un tool porta un allegato / il router ha detto "profondo" / i risultati superano N caratteri
                                                                                     ▼
          DEEP: stesso provider, il modello che legge documenti e vede immagini
                                                                                     ▼
          risposta finale + chip → AskResult (risposta, uso, tool, livello raggiunto, log)
```

- **Tre livelli per provider** (`ModelTier`): `ROUTER` piccolo e veloce, `CHAT`, `DEEP`. I default
  di router e chat sono in `AiDefaults`; il profondo lo sceglie `TierDefaults.pickDeep` dal catalogo
  vivo alla verifica della chiave, e l'utente puo' cambiarlo (`AiSettingsStore.setModel`).
- **Gli allegati** viaggiano come `ContentPart` dentro un `Message.User`: Gemini li prende in linea,
  OpenRouter i PDF li legge col suo parser (`plugins: file-parser`) e le immagini dove il modello
  vede, Groq vede solo coi modelli che lo dicono nel nome e non legge documenti. Quando il modello
  profondo non regge una parte, l'orchestratore chiede all'app di tradurla in testo
  (`attachmentFallback`); se l'app non sa farlo, lo dice al modello.
- **Un flusso che si spezza a meta'** — la rete cade, il server chiude, un pezzo non si legge —
  dopo aver gia' portato del testo o una tool call si rifa' **senza stream**, una volta, prima di
  passare al failover. Un rifiuto (chiave, 400) non si riprova.
- **Il failover** e' una tabella (`FailoverPolicy`): 429 -> il prossimo provider, o l'attesa del
  `retry-after` se non c'e' nessuno; 5xx e rete -> una riprova, poi il prossimo; chiave sbagliata ->
  ci si ferma e lo si dice.
- **Il budget** (`AiOrchestratorConfig`) e' dell'app: una card che aspetta a schermo vive con 90
  secondi, un service in background con quattro minuti.

## Cosa non fa

- Non persiste niente oltre chiavi e impostazioni. `Conversation` e' in memoria: un'app che vuole
  la cronologia la salva da se' (bastano gli `Exchange`; il traffico tool si perde e va bene).
- Non disegna. Nessuna dipendenza da `engine-ui`.
- Non conosce nessun dominio: se un tipo qui dentro sapesse cos'e' un voto, sarebbe nel posto
  sbagliato.

## Dalla 1.26.0: allegati dell'utente, catalogo gerarchico, ricerca web, consumi

Cinque aggiunte, tutte con un default che lascia le app di prima come stavano.

- **Gli allegati dell'utente.** `AskInput.attachments` porta le parti (uno screenshot, una foto, un
  PDF) che l'utente ha messo nella domanda. Entrano nel suo messaggio se il modello della chat le
  regge; se le regge solo il profondo si parte dal profondo; se non le regge nessuno passano da
  `attachmentFallback`, come gli allegati dei tool. L'ultimo scambio le ricorda (`Exchange.attachments`)
  e il compattatore le ripropone solo per lui, facendole cadere per prime quando il budget non basta;
  cambiando provider, un allegato che il nuovo modello non regge diventa una riga che dice che c'era.
- **Il catalogo gerarchico.** Un gruppo puo' dichiarare una `category` (`AiToolCategory`: un'app,
  un'area), un `parent` (un terzo livello) e `loadsWithCategory` (si apre con la categoria). Se
  qualche gruppo ha una categoria il registry e' `hierarchical`: lo stadio 1 (`AiRouter(...,
  categories = ...)`) sceglie **una categoria o "nessuna"** e fino a quattro sue sottocategorie; al
  posto di `altri_tool` il modello riceve `apri_categoria` (tutte le categorie con la loro riga) e
  `apri_sottocategoria` (le sottocategorie delle categorie aperte). Cio' che si apre **resta nella
  `Conversation`** (`loadedGroups`, `loadedCategories`) per le domande dopo; oltre
  `AiOrchestratorConfig.maxLoadedTools` cadono i gruppi usati meno di recente; `maxOpens` limita le
  aperture in una domanda. Su OpenRouter il catalogo gerarchico non parte intero: valgono i gruppi
  aperti e `routerHint`. Un'app con un solo dominio non dichiara categorie e non cambia niente.
- **La ricerca web.** `ChatRequest.webSearch` chiede al provider di cercare prima di rispondere:
  Gemini con `google_search`, OpenRouter col plugin `web` (`webSearchMaxResults`), Groq passando al
  modello `groq/compound-mini` (che non accetta strumenti: la ricerca va fatta in una chiamata a
  parte, senza tool, di solito da un tool dell'app). Le fonti tornano in `ChatTurn.citations` e in
  `ChatDelta.Finish.citations`.
- **I consumi.** `AiOrchestrator(usageSink = ...)` riceve un `AiUsageEvent` per **ogni** chiamata a
  un provider — il router, ogni giro, la riprova senza stream, e anche quelle fallite (con
  l'errore e i limiti letti dagli header). L'engine non li persiste: e' il gancio per un tracker
  dell'app.
- **I metadati dei tool.** `AiTool.needsConfirmation`, `longRunning`, `isAction` e `describe(args,
  ctx)` dicono a chi esegue un tool da fuori dell'app (un bridge verso un altro assistente) se
  chiedere conferma prima, se aspettarsi un lavoro lungo, se e' un'azione; dentro l'app non cambiano
  niente.

## Migrare un'app che aveva `core-ai`

FluidWeather e Fluid Transit hanno ancora la loro copia. Per passare a `engine-ai`:

1. `engine-install.ps1 -Modules engine-ai` (o aggiungere il modulo al blocco nel `settings.gradle`).
2. Sostituire il package `…core.ai` con `dev.antigravity.fluidengine.ai`.
3. `ToolGroup` (enum) diventa un enum dell'app che implementa `AiToolGroup`; `AiTool` prende il
   tipo del contesto e ritorna `ToolOutput(text)` invece di `String`; `ToolRegistry` vuole i
   gruppi e il gruppo delle azioni.
4. `ToolContext.actionsEnabled` passa in `AskInput.actionsEnabled`; `PromptBuilder.forceFinal` in
   `AskInput.forceFinalPrompt` (o il default `AiPrompts.forceFinal`).
5. `AnswerChip` non conosce piu' `OpenTarget`: e' `(id, value)`, l'app lo traduce.
6. `KeystoreCipher(alias = "fluidweather.ai")`: **l'alias di prima**, o le chiavi salvate non si
   leggono piu'.
7. Il contatore `openrouter_free_*` non c'e' piu' (era codice morto in entrambe le app).
